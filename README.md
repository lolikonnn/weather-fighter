| ![行情头](docs/screenshots/quote-head.png) |

> 就是主图正上方那一块。左边是天气 + 价格，右边一格一个数，**按同类分了五行**：
> 今天有多热（最高 / 最低 / 体感 / 全天波动）、风（风速 / 风向 / 平均风速 / 气压）、
> 天上有什么（云量 / 紫外线 / 湿度 / 降水）、日月（日出 / 日落 / 昼长 / 月相）、
> 读数基准（今日 0 点 / 昨日 23 点 / 同期 / 观测点）。
>
> 月相没有任何数据源直接给，是按朔望月自己算的；昼长优先用数据源的日照秒数，没给就拿日出日落相减；
> 云量和紫外线取的是**当前这个小时**的值（抬头看一眼天，和这个数对得上才有用）。
> 算法和取舍都写在 `docs/NOTES.md` 里。
>
> 最下面那条**预警滚动条**是行情软件里"滚动播报"那个位置。它**只滚当前正在看的那座城市的预警**
> ——自选里切到哪座城市，条子就跟着换（不是“定位在哪就永远滚哪”）；标签上会写清是哪座城市。
> 筛法**不是按距离画圈**（画圈会把隔壁市的一起卷进来），也不只是"把城市名拿去标题里找" ——
> 那样子串会撞上**同名**：青海省的「海南」和海南省、「吉林市」和「吉林省」、北京的朝阳区和长春的
> 朝阳区…… 2026-10-10 修过一次：现在**先认省**（气象局的标题是「<省>[<市>[<区>]]发布…」），
> 省对不上就直接否掉；同一个省里再看有没有点名本城/本区；**标题只点了省的那种（省级预警）省内所有城市与区县都算** ——
> 所以「海南省发布暴雨蓝色预警」全省可见，而它不会再跑到青海去。在看区县时会把上级市一起算进来
> （区一级常常没有自己的预警）。这个区市一条都没生效的时候**整条收起来**，不留"暂无预警"占位。
> 内容比可视区短就静态显示，长了才自己慢慢往左走（26 像素/秒）。
> **手指可以随时横向拖、桌面滚轮也能滚** —— 一碰它就停下来让位，松手几秒后接着走。
> 系统里开了「减少动态效果」时不自动走，但仍然拖得动。
> 整条可以点，点开就是完整的预警信号面板（横向拖过就不算点，免得想拖一下却跳进面板）。

## 这是什么

一个把**气温当成股价**来展示的天气软件。整个交互、配色、术语都照搬 A 股行情终端：

| 股票里的东西 | 这里对应什么 |
| --- | --- |
| 股票代码 | 城市代码（中国天气网的 `101010100` 这类 9 位码） |
| 最新价 / 涨跌幅 | 当前气温 / 相对昨日同一时次的变化（**分母用绝对温标**，见下） |
| 分时图 | 今天 00:00–23:00 的逐小时气温，含均价线、昨收虚线 |
| 日 K / 周 K / 月 K | 每天的开盘价 = 当日 00:00 气温，收盘价 = 当日 23:00 气温，最高/最低 = 当日极值 |
| 成交量（现在叫「温差」） | 日内最高温 − 最低温；底部副图页签可切到 **降水 / 风 / 云量 / 空气** |
| MA5 / MA10 / MA20 / MA60 | 最近 5 / 10 / 20 / 60 天的平均气温，看大方向 |
| MACD / KDJ / RSI / BOLL / WR | **已经删掉了** —— 这几个股票指标对看天气没用，换成了下面「天气功能」里的真东西 |
| 五档盘口（卖五~卖一 / 买一~买五） | 未来 5 天的**预报最高温**（卖盘，由高到低）与**预报最低温**（买盘，由低到高） |
| 成交明细 / 逐笔 | 最近 60 个逐小时观测，涨跌按对上一时次着色 |
| 自选股 | **「城市收藏」**（跟电商里的「商品收藏」同一个构词）。**第一次打开会预置 北京/上海/广州/深圳/长沙/武汉**（只在这一项从没存过时塞；把收藏删光就照实为空，不会再冒出来）。增删就点那颗星：**空心 ☆ = 没收藏，实心 ★（金色）= 收藏了**，全站统一这一个符号。星的位置分两档、**两种档位的横坐标都钉死成一条线**（名字格固定 90px，所以星不随名字长短飘）：**桌面端**紧跟城市名，**手机端**在城市名与涨跌之间那片空档、跨两行垂直居中。**名字比格子长时（区县全名最长 15 字）——桌面端只给「选中那一行」开横向滚动**把名字看全（动内层、外层格子不动，所以星不晃）；手机端名字格占满剩余宽度、根本不超出，不滚。可按涨幅或名称排序、**长按某一行还能上下拖动自定义顺序**（松手即保存）；**行情头城市名旁边那颗星点一下就能加/取**。加城市走搜索框或「全部城市」抽屉（352 城）——**原来的「热门城市」那块已删除**（项目初期的试验内容） |
| 行情刷新频率 | 1s / 3s / 5s / 10s / 30s / 1m / 5m / 手动 |
| 涨跌配色 | 红涨绿跌（A 股）/ 绿涨红跌（美股）一键切换 |
| K 线实体 | **涨空心、跌实心**（A 股习惯）。气温 K 线比真股票密集得多，全实心会糊成一片色块；空心后涨跌一眼可辨。实现上就是把 `itemStyle.color` 设成 `transparent` 只留描边，影线走 `borderColor` 所以仍是涨色 |
| 平盘日 | 画**中性绿**（`--flat: #00b578`；2026-10-07 从灰改成绿，"持平的灰色改为绿色吧"）。开盘价取当日第一个有效整点、收盘价取最后一个，两者相等就是"一天下来没升没降"—— 实测 576 个交易日里有 **19 天（3.3%）**。这种日子既不红也不绿，量柱也同色，跟 tooltip 里的 `U.trendColor()` 一致 |
| 涨跌幅的尺度 | 气温是**间隔尺度**量，摄氏 0 度是人为约定的，所以比值的分母必须加上 273.15 换成绝对温标。否则 0℃ 以下**符号会整个翻转**（实测哈尔滨 90 个交易日里 88 天收盘价在 0℃ 以下、其中 47 天"升温却显示成负数"，最离谱的一天大降温 11.3℃ 却显示 `+235.4%`）。换算之后涨跌幅落在 **±0.2%~2.5%**，恰好是真实股票一天的波动区间 |
| 数据来源与兜底 | 每个城市先试**中国气象局**的官方站号（实况最准），取不到就退回 **Open-Meteo**。注意气象局的"没有观测"不是一个空值，而是一整套 **`9999` 哨兵**（数值字段 9999、字符串字段 `"9999"`、`lastUpdate` 停在最后一次正常上报）—— 澳门/台北这类长期停报的站会一直返回它。所以实况一律先过 `cleanNow()` 清洗，洗完没有可用温度就**当没取到**走 Open-Meteo，而不是把 9999 显示成 `9999.0℃ / +3358%` |

> 关键前提：**气象局那三路（实况 / 官方预报 / 官方日历）跟 Open-Meteo 是互相独立的**，
> 那种情况下它们照常返回。所以：
> ① 三份"贵且不太会变"的响应各占一个 `localStorage` 槽位（`arch` 历史逐小时 / `fcst` 近期+预报 /

> （`arch` 30 天、`fcst`/`min` 14 天）。过期的 K 线照样是那条 K 线，比一张空图强得多。
> ② 历史逐小时的 archive 主机挂了还会换 `historical-forecast-api` 那台（配额是分开的）。
> ③ **降级合并**：新拿回来的那份如果只有气象局几路（曲线是空的），就**把实时的行情栏字段贴到
> 历史曲线上**，而不是拿空曲线把好曲线顶掉。
> ④ **盘口不依赖 Open-Meteo**：`obList()` 优先吃 `fcst.daily`（官方 5 日预报）；以前它先检查
> `d.daily` 非空才往下走 —— 额度一用尽就显示"暂无预报数据"，那条守卫已经拆了。
> ⑤ 空曲线时主图上会写明**原因**，不是干巴巴一句"暂无K线数据"。
> ⑥ 「点击做空天气」只硬依赖 15 分钟行情，给它持久缓存就能照常开局。
>
> > 实测（`tmp/degrade.js`，真实现场）：报价头 **22.9℃ +6.4 +2.21%**、
> > **盘口 12 个子元素 / 官方 5 日预报齐全**、有历史快照时曲线一根不少且 `now` 是刚拉的、
> > **游戏也能开局**（`连接状态 = 行情推送中`）。

| --- | --- |
| 温差 | 日内温差（最高 − 最低） |
| 降水 | 降水量柱（左轴 mm）+ 降水概率线（右轴 %） |
| 风 | 风速柱（按蒲福风级着色）+ 阵风虚线 + 顶部风向箭头 |
| 云量 | 低云 / 中云 / 高云堆叠面积 + 总云量线 |

副图右侧还有一个 **「📈 叠到主图」** 按钮：把当前副图的口径**拉一条线画到上面的主图**上
（降水 → 青色降水量线、风 → 绿色风速线、云量 → 灰蓝云量线、空气 → 紫色 PM2.5 线）。
这条线走主图**最右侧的第 3 根 Y 轴**（`offset:44`），不跟百分比轴抢刻度；按钮状态会记在
`localStorage` 里，副图切回「温差」时自动置灰。口径与主图对齐**统一按时间键查表**，不是按下标 ——
按下标会在「分时/7日」上整体错位（主图是「今天 24 小时 / 昨天→未来五天」，而聚合序列是
「从现在往前 2 小时起 24 小时」）。

> **日界明暗带**：7日 / 多日折线图按自然日铺**明-暗交替**的底色（7 天 = 四明三暗），
> 并在每条日界画竖虚线，一眼能看出一天一天的界限。单日分时（只有一天）不铺带。
> 带子挂在一条不画线的独立系列上（`z:1`），保证永远在气温线和均价线之下。

选**分时**就是今天的逐小时，选**7日**就是逐小时 **168** 个点（昨天 + 今天 + 未来五天），
选**日 K** 就按天聚合最近 60 天，
选**周 K / 月 K** 就按周 / 按月，选**预报 K** 就是**最近 10 天 + 未来 16 天**（一共约 26 根）。
聚合口径按物理量定：
降水量**求和**、降水概率取**最大**、风速阵风取**最大**、云量和 PM2.5/AQI 取**平均**；
风向不能平均，取「风最大的那一刻」的风向。

> 预报 K 的窗口以前是往回留 45 天，图上四分之三都是历史 —— 过去的占比过多，
> 现在历史只留 10 天当参照，重心全部让给预报。

周期页签的「7日」口径是 **昨天 + 今天 + 未来五天**（共 168 个逐时点）——
天气预报最要紧的就是后面这几天，所以窗口是往前压的，不是往回看。
窗口的尾端**故意停在"未来第五天"**：右侧栏那块「未来 5 天高低温」列的就是这五天，
两块图上下对着看，正好一一对应。

> **7日图的横轴会写日期**：`10-05 12:00 10-06 12:00 …`，每个自然日一格日期，
> 正好压在明暗带的交界上，和上面说的日界带是一套东西。
> 这里踩过一个坑：轴标签的 `S.seven` 标志**从来没被传进去过**（`seriesFor()` 的返回对象里没有这个字段），
> 所以 formatter 分支永远走不到，横轴只有 `00:00 / 12:00` 而没有日期。

> **这一档的「温差」副图也跟着主图走，而且逐小时那两档换了口径。**
> 温差（当日最高 − 当日最低）是**每天**的量：一天一个数，摊到 24 个小时上就是一条平线
> （分时档下整幅图只剩一根柱子）。所以**分时 / 7日 改成「较当日均温」**：
> 这一小时的气温比当天平均冷暖多少，围绕 0 上下，每天一个完整的波。
> **日K / 周K / 月K 仍然是"当天的日内温差"** —— 那里一天本来就是一根柱子。
> 横轴类别直接用主图的时间键，上下两块图一格对一格。
> 以前它不管主图什么周期，一律画 553 根日K：主图 24 小时、副图 553 天，说的不是同一段时间。

### 为什么标的是「天气指数」而不是气温

第一版直接拿气温当价格，收到了很准的差评：

> 不太行，因为必然大趋势是冬天降温夏天升温。太稳定了没有什么感觉，只要稳住总会升/降的。

问题在于**气温是个太温和的信号**。它有昼夜循环、有季节趋势，一个小时才挪一两度，
做成 15 分钟 K 线就是一条几乎水平的线 —— 抱着不动就能赢，盘感无从谈起。

真正有波动的是**对流**：CAPE（对流有效位能）能从 0 冲到 5000、阵风能从 2 m/s 冲到 60、
降水绝大多数时刻是 0、打雷时才爆。所以标的是 **WXI 复合天气指数** —— 而且它**有语义**：
**指数高 = 当地天气好，指数低 = 天气差。**

```
① 舒适度 comfort ∈ [0,100]（有绝对含义，不是"偏离常态多少"）
   体感温度 0.34 + 湿度(露点) 0.15 + 降水 0.21 + 天气码 0.20 + 阵风 0.05 + 空气 0.05

   晴/基本晴 ≈ 81.5    多云/阴 ≈ 79.9    毛毛雨 ≈ 74    阵雨 ≈ 65
   雷暴 ≈ 57           雷暴+冰雹 ≈ 50    （广州 92 天实测）

② 基本面 anchor = 1000 + (慢速comfort − 中位) × 8
   "慢速"是半衰期 12 小时的 EMA —— 即时 comfort 会被单根雷暴砸出大坑

③ 价格 —— 事件驱动，不是"连续噪声 + 慢回归"
   每根按到达率生成若干笔"成交事件"，每笔带一次价格冲击：
     impactState = impactState × (1 − INERTIA) + Σ事件冲击
     价格         = anchor + impactState
```

**指数涨 = 天气转好，指数跌 = 天气变差。** 本质是在赌对流。

#### 为什么用「事件驱动」而不是「连续噪声」

真实 15 分钟行情有个很硬的特征：**lag-1 自相关 ≈ 0**（实测欧易 10 个交易对是
−0.05 ~ +0.02）—— 也就是**几乎无记忆**，上一根涨跌对下一根没有预测力。

而"连续噪声 + 慢速均值回归"这种写法**做不到**这件事：

```
px = pxPrev + (anchor − pxPrev) × REVERT + noise
     ↑ 前景价格出现在等式右边 → 必然产生 AR(1) 记忆
```

只要回归慢（为了钉住基本面），滞后一阶相关就 ≈ 1−REVERT。实测锁死在 **0.38**，
扫 27 组参数下限就是 0.35 —— 数学上的必然，不是没调对。

真市场是**事件驱动**的：一笔成交到达 → 一次价格冲击 → 按韧性**快速衰减** → 下一笔再来。
所以新版把价格**定义**成两个互不依赖的状态之和，前景价格不再出现在等式右边：

```
impactState = impactState × (1 − INERTIA) + Σ单笔冲击     // INERTIA = 0.92
价格         = anchor + impactState
```

关键在**衰减与到达的相对速度**：衰减慢于到达 → 冲击首尾相接 → 又是 AR(1)；
衰减快于到达 → 每笔基本独立 → 自相关降下来。顺带白拿两个真市场特征：

- **波动聚集**：到达率**自激** —— 来的事件多，下一根的到达率就更高
- **肥尾**：单笔冲击用**幂律尾巴**，多数很小、偶尔一次清算瀑布

三项一次对上：

| 指标 | 真实 BTC / WIF | 旧架构 | **事件驱动** |
| --- | --- | --- | --- |
| p90/中位 | 3.50 / 3.25 | 4.2 | **3.95** |
| p99/中位 | 8.76 / 7.69 | 15.6 | **8.6** |
| 单根最大 | 4.2% / 38% | 8.5% | **26%** |
| 峰度 | 16 / 472 | 5~13 | **42** |
| lag-1 自相关 | −0.01 ~ +0.02 | 0.38 | **0.17 ~ 0.28** |

### 复合：大盘、露点、盘子扰动

复合指数最早是这样设想的：

> 把某个地区里所有城市的温度做平均加权，得到的值就当作该地区的大盘指数，这样才有可炒的东西
> 从温度变成一个由大盘指数、当地温度、空气质量以及未来的预报等所共同决定的一个新指标。
> ……不然太没有挑战性了。……然后非常小的那种地方，比如小县城之类的，可以把这个随机扰动加大，
> 模拟一下庄家操盘。

所以现在图上多了一条**紫色虚线的大盘**（`REG_C = '#c792ea'`）。它的构成和哪几项是真的：

| 项 | 真假 | 怎么来的 |
| --- | --- | --- |
| 本地 WXI | **真数据** | `minutely_15` 的气温 / 露点 / 降水 / 天气码 / 阵风 + `pm2_5` |
| 区域大盘 | **真数据** | 同省最多 8 城的 15 分钟**逐变量平均**，再套同一套 `comfort()` |
| **空气质量** | **真数据** | `air-quality-api` 的**逐小时** `pm2_5`（92 天），对齐到 15 分钟根 |
| **地震** | **真数据** | USGS 目录里震中/震级/时间，按到本城的大圆距离算冲击 |
| **台风** | **真数据** | 中央气象台 `typhoon.nmc.cn` 的路径点，逐根插值出中心距离与风速 |
| **预报偏离** | **真数据** | `previous-runs-api` 的 `_previous_day1`（提前 24 小时的预报）与实测之差 |
| 盘子扰动 | **建模** | 带衰减的随机游走，振幅按行政层级放大 |
| 成交事件 | **建模** | 到达率 + 幂律幅度（见上）；驱动量（天气、盘子）是真的 |
| K 线上下影线 | **建模** | 15 分钟粒度拿不到根内极值：基础影线按 `|涨跌|×0.30`，另叠**插针** |

三件想说明白的事：

1. **大盘是真的**，不是编出来的一条参考线。Open-Meteo 支持**一次请求多个坐标**
   （`latitude=a,b,c&longitude=x,y,z` 直接返回数组），所以同省 8 城只要**一个请求**，
   不额外吃额度。取的是和单城完全相同的变量集，所以能直接喂给同一套 `comfort()` ——
   如果只平均气温，那等于把"趋势"又算了一遍，因为气温太慢太平。
2. **没有按人口加权**。`cities.json` 里只有 `id/name/prov/py/lat/lon/cma/path`，**没有人口字段**，
   所以就是等权。等权就等权，不假装。要加权得先找一个人口数据源，那是另一件事。
3. **"盘子扰动"是唯一一个纯建模项**（加上影线），而且它**故意**在小地方更大：
   `cities.json` 里没有人口，就按**行政层级**分档 —— 直辖市 3.0 / 省会 2.2 /
   有国家站的地级市 1.6 / 有 `path` 的 1.2 / 区县 0.6，取 `1.6 ÷ 该值` 当振幅倍率
   （夹在 `[0.35, 2.6]`）。所以广州（有国家站，1.0×）和惠州（无站无 path，2.60×）
   开出来的行情手感是不一样的 —— 小地方的"庄家操盘"是在这儿体现的，不是靠调大随机数。
   它触发时会在屏幕中间闪一条 **🏦 大单扫货 / 📉 有人出货**。

   顺带：`G.regLine` 是**本局窗口那一截**（长度 = 当前档位的一局根数 `roundBars()`），不是整段 92 天。
   早期实现画线时多加了一个 `G.regFrom` 偏移，结果那条线在图上**长度是 0**、根本不显示 ——
   探针把 `大盘 series data 长度 = 0` 打出来才发现的。

大盘线**不参与 Y 轴范围计算**，否则它会把蜡烛压扁；它只是个参考指标，不是可交易的合约。

### 四个"压力源"，外加一整套"天文家族"

群里还说了：「如果有什么台风消息地震消息还可以再做一个新的压力源」「反正当地的什么情况，
乱七八糟的参数加进去就好了」。照做了，四项全部接**真数据**：

| 压力源 | 数据源 | 落进指数的形式 | 实测覆盖（广州一段 3552 根） |
| --- | --- | --- | --- |
| PM2.5 | `air-quality-api.open-meteo.com` 的 `hourly=pm2_5` | 稳健标准化后乘 `AIR_K = 6` —— **慢变量**，管的是整段的偏置 | 99.3%，极值 ±47.5 点 |
| 地震 | `earthquake.usgs.gov` 的 `fdsnws/event/1/query` | 事件冲击：`QUAKE_K × (震级 − 3.0) × (1 − 距离/700km)`，之后按 `0.90` 衰减 160 根 | 0.5%（本来就 rare） |
| 台风 | `typhoon.nmc.cn` 的 `list_<年>` + `view_<id>` | **逐根**插值出台风中心，`40 × (风速/30) × (1 − 距离/900km)²` | 53.1%，极值 +9.4 点 |
| 预报偏离 | `previous-runs-api.open-meteo.com` 的 `temperature_2m_previous_day1` | 实测 − 提前一天的预报，稳健标准化后乘 `FCST_K = 2` | 95.8%，极值 ±15.5 点 |

几个实现上的关键点：

- **空气质量只能逐小时**。`air-quality-api` 的 `minutely_15` 返回的 `time` 数组长度是 **0**
  （参数照收、HTTP 200，只看状态码发现不了）。所以 PM2.5 走 `hourly` + `past_days=92`，
  再按小时键对齐到 15 分钟根。**它照样是 92 天的真数据，不是拿 `current` 糊的。**
- **地震为什么要经 Wolfx 转发**：中国地震台网自己的站点 `www.ceic.ac.cn` 响应 200 但**不带 CORS 头**，
  浏览器里直连读不到；Wolfx（`api.wolfx.jp`）把 CENC 的数据带 `Access-Control-Allow-Origin: *` 转了出来，
  所以借它转发；另一路 USGS 免 key + CORS 全开，负责 130 天窗口与全球覆盖。
  两边按「±10 分钟且球面距离 ≤100 公里」判重，重复时保留 CENC 那条（中文地名更有用）。
  顺带主站天气页也因此有了 🌋 地震面板（见上面截图）。
- **台风的列表是倒序的**。`list_2026` 按新→旧排，只取最新 12 个会把 92 天窗口里
  真正逼近华南的台风全切掉（沙德尔 211km / 紫檀 350km / 美莎克 477km 都在 7~8 月，
  而最新的 12 个是 9 月底之后的）。所以取 **30** 个，并发限流 4，TTL 6 小时。
- **预报偏离的写法是个坑**：正确写法是**变量名加后缀**，不是参数。
  `temperature_2m_previous_day1` 表示"比有效时刻早 24 小时做出的那次预报"。
  所有 `models=xxx_previous_dayN` 的写法都会 **HTTP 400**；
  而 `previous-runs-api` **不加后缀**时返回的数据与 `historical-forecast-api`
  **一模一样**（864 个时刻一字不差），一度让人以为它只是个别名。
- **只在上升沿播报**。这四项都是有惯性的状态量，不加判定的话一局 3552 根里会弹 540 次
  "台风影响"。现在用 `rise(f, 阈值)` / `fall(f, 阈值)` 只在**第一次越过**时播，
  于是一局里台风只剩 4~5 条、地震 0~1 条，其余是天气与盘子消息。
- **窗口偏置**：92 天里台风/地震真的拢共就那么些，纯随机切窗口大多数时候覆盖不到。
  所以 **50% 的局挑"事件分最高"的那十天、50% 纯随机** —— 不是"每局必有事件"，
  那就成安排好的剧情了，也就没有“不知道这段是哪年月”这个前提。
- **取不到就退化成 0，绝不编数据**。六个源各自独立 `catch`，任何一项挂了
  只影响它那一项。

调参是量出来的，不是拍的（`QUAKE_K` / `FCST_K` / `TYPHOON_K` 各改过一轮）：

- 第一版 `FCST_K = 7` 跑出预报项 `min=-59.5 max=+54.8` —— ±6% 的抖动全来自预报误差，太猛，砍到 **2**。
- `QUAKE_K = 6` 时 M4.6 / 653km 只值 0.64 点，等于没有，提到 **12**。
- `TYPHOON_K = 60` 时 211km / 52m/s 会直接顶到 60 点，降到 **40**。
- 最终整局振幅中位数 **25.1%**（加这四项之前是 26.8%，但窗口口径换过，可比性有限）；
  单根中位涨跌仍是 0.266%。

#### 天文家族：九条天文通道拧进同一根指数

同一个人后来又说：「模拟游戏要的不是真实而是戏剧性，要刺激」，以及「天文那些也接进去吧」。
接的是**本地算得出来的那九样**，全部落进 `skyHeat` 这一个标量，再由它去拧**事件到达率**、
**混沌跳跃的概率与幅度**、以及**插针概率**：

| 通道 | 系数 | 语义 |
| --- | --- | --- |
| 月光（照亮百分比） | `MOON_K = 8` | 满月把暗目标全糊掉 |
| 流星雨（极大前后） | `METEOR_K = 80` · 流量 `METEOR_FLOW = 2.5` · 衰减 `METEOR_DECAY = 0.985` | 爆发夜 |
| 超级月亮 | `SUPER_K = 70` | 近地点满月 |
| 银心高度 | `GALAXY_K = 22` | 银河中心越高越"看得见" |
| 头顶亮星与行星 | `STAR_K = 8` | 此刻能数出几颗 |
| 天文夜长度 | `NIGHT_K = 20` | 天真正黑透的那一段 |
| 潮汐（大潮／小潮） | `SPRING_K = 26` | 朔望那几天 |
| 城市光污染等级 | `LP_K = 12` | 1~9 级 |
| 地磁暴 Kp | `Kp_K = 45` | 极光那一路 |

`skyHeat = Σ|各项| ÷ 100`（夹在 0~2），再用 `HEAT_FLOW = 3.0` / `HEAT_CHAOS_P = 9.0` /
`HEAT_CHAOS_K = 1.5` / `HEAT_SPIKE = 6.0` 去拧到达率、混沌与插针 ——
**输入全是真数据，手感是为戏剧性调的**。同一批种子做 A/B（28,416 根）：
p90 **×1.750**、p99 **×1.763**、单根最大 **×1.963**，涨跌 >1% 的根数 **1444 → 4244**，
单局振幅中位数 **21.8% → 34.3%**，NaN **0** 根。

| 挂单 | 限价单（挂多 / 挂空）+ 止损、止盈各一张，**挂单会冻结保证金** |
| 天气日历 | 只提示**什么时候**变天，**不提示往哪边** |
| 中途退出 | **不作废**。行情按**真实流逝的时间**继续走（见下节），下次进来接着玩 |
| 结算 | 跑满自动结算，按 `最终权益 / 本金` 评级 S/A/B/C/D/E/**SSS**（爆仓固定 F）。结算卡上两句：**评语**说这一局发生了什么，**收场白**是最后一句 —— 八档都有，**语气是欠揍雌小鬼，等级越低越嚣张**；句子里凡是提到杠杆的，**数字按这一局的真实倍率现算**（1× / 5× 那句本来就不提数字） |

**为什么数据是 15 分钟而不是"更细"**：常见疑问是能不能做到每分钟 / 每半小时。实测结论是 ——
`minutely_1` 和 `minutely` 在 Open-Meteo **不存在**：参数照收、HTTP **200**，但 `time` 数组长度是 **0**
（和 `past_days=92` 悄悄返回一串 `null` 一样，**只看状态码发现不了**，得数数组长度）。
所以 15 分钟就是免费源能给到的最细粒度。**比 15 分钟粗的档（30 分 / 1 时 / 4 时 / 1 日）
是把 15 分钟的真数据并起来看，1 分 / 5 分两档则是插值展开的**（见下节）。

> 顺带一提：群里说的"最小只有一个小时"指的是**主站天气页的分时图**
> （`web/js/weather.js` 走的是逐小时）—— 那是另一个页面，不是这个游戏。

#### 七档 K 线周期：哪几档是真数据，哪几档是画出来的

| 档位 | 一天几根 | 一局几根（7 + 30 天） | 预热段 | 交易段 | 怎么来的 |
| --- | --- | --- | --- | --- | --- |
| 1 分 | 1440 | 53280 | 10080 | 43200 | **插值展开**：1 根 15 分钟摊成 15 根 |
| 5 分 | 288 | 10656 | 2016 | 8640 | **插值展开**：1 根 15 分钟摊成 3 根 |
| 15 分 | 96 | 3552 | 672 | 2880 | 数据源原样 |
| 30 分 | 48 | 1776 | 336 | 1440 | **真数据聚合**：2 根并 1 根 |
| 1 时 | 24 | 888 | 168 | 720 | **真数据聚合**：4 根并 1 根 |
| 4 时 | 6 | 222 | 42 | 180 | **真数据聚合**：16 根并 1 根 |
| 1 日 | 1 | 37 | 7 | 30 | **真数据聚合**：96 根并 1 根 |

档位名和排列照着一张真实行情软件的截图（`1分 5分 15分 1时 4时 1日`）来的。

展开的做法是：收盘价沿父根的开 → 收线性走，再叠一个**确定性**小锯齿
（`zag(i, j)`，用的是 `sin` 哈希而不是 `Math.random()` —— 否则同一段行情每次长得不一样，
探针根本没法验收），影线按父根振幅的比例分下去。**最后一根强制收在父根收盘价上**，
所以把 1 分钟档聚合回 15 分钟能和真数据**逐点对上**（探针实测误差 0）。

> 换句话说：**切到 1 分钟不会增加信息量**，只是把同一段天气画细了。
> 七档的首开价和末收价完全相同，起点时间也相同，走势是同一套。

价格模型本身**只跑一遍**、永远按 15 分钟的 3552 根算，重采样是在它之后做的 ——
所以不存在"1 分钟档和 1 日档走势不一样"这种荒唐事。

**局中换周期**：不重新取数据，而是拿开局留的那份 15 分钟原样序列重采样一遍，
再把"已经推进到第几分钟天气"映射到新周期的下标上。映射只认**已经走完**的那些根
（`G.i = floor(nowMin / 周期) - 1`）—— **绝不往前跳**，否则换到粗周期时现价会瞬间变成
一段**未来**天气的收盘价，白白扫掉止损。代价是切到更粗的档时会往回退最多一个周期
（探针实测：切到 1 分 / 5 分 / 15 分 / 30 分 / 1 时**退后 0 分钟**，切到 4 时 / 1 日退后 60 分钟）。
持仓、挂单、权益曲线都原样保留。

#### 关掉页面，行情还在走

「退出游戏就作废」是很没道理的一件事：**现实里的股票不会因为没打开同花顺就不动。**
所以退出不清进度，而且**离线的那段时间行情照走**。

| 操作 | 结果 |
| --- | --- |
| 点面板右上角的 ✕ / 点遮罩 / 按系统返回 | 弹一张卡：**保留进度** / **结束本局** / **取消**（「取消」= 什么都不做，局继续跑） |
| 选「保留进度」 | 存档落地，面板关掉，行情**从此刻起按真实时间继续走** |
| 选「结束本局」 | 存档清掉，这局作废 |
| 直接关标签页 / 关 App / 手机切后台 | `pagehide` + `beforeunload` 兜住，等于自动选「保留进度」 |
| 在**同一个城市**再点小游戏 | 卡上两个选项：**继续 <上次那个城市>** / **从 <当前城市> 重新开始** |
| 在**别的城市**点小游戏 | 同上 —— 「继续」会回到上次那座城市接着玩（不会把 A 城的行情套到 B 城头上） |

**离线追赶怎么算的**：速度档的单位本来就是「**每真实秒推进多少分钟天气**」，
所以 `补的根数 = 离线秒数 × 速度档 ÷ 当前周期`，直接拿它去跑 `stepBars()` ——
和在线时走的是**同一段代码**，滑点、手续费、挂单成交、爆仓判定、新闻一律照常发生。

```
离开 25 秒   → 补 100 根（15 分档 · 悠闲）
离开 2 分钟  → 补 480 根
离开 40 小时 → 直接跑到 30 天交易期结束，自动结算
```

补完之后会弹 toast「你不在的时候行情走了 N 根」。**这段时间不会静音地放过**：
如果离线期间爆了仓，回来看到的就是爆仓结算 —— 这跟现实一致。

**存档里存的是 15 分钟的 `base` 序列（3552 根 · 约 525 KB），不是当前周期的 `series`。**
1 分钟档的 `series` 有五万多根，塞进 localStorage 会直接把 5 MB 配额撑爆；
存 `base` 则与周期无关，恢复时拿 `resample()` 重采样一遍就回来了 —— 这也正是局中换周期走的同一条路。

#### 设置会记住上次那一套

面板上的**本金 / K 线周期 / 行情速度 / 杠杆 / 仓位 / 音效**六项，调过就记住：结束一局、关掉页面、
明天再进来，还是上次那个样子。**尤其是「行情速度」** —— 以前它每次都被打回默认的「悠闲」，
选过「狂暴」的人每次都得重选一遍。

设置跟「进行中的那一局」是**分开存**的两份东西：

| 存的东西 | 键 | 什么时候会被清掉 |
| --- | --- | --- |
| 进行中的那一局 | `wxgame_save` | 点「结束本局」、到期结算时清掉（局确实没了） |
| 调好的设置 | `wxgame_cfg` | 基本不清 |

两者的先后关系：**开局先读设置当默认值；存档里带着的那套优先**（因为那是"当时正在用的"），
恢复存档时顺手把设置也刷成存档里那套 —— 所以结束一局之后再开局，还是最后一次用的那一套，
不会退回初始值。非法值（比如换过版本之后某个档位没了）会被丢掉、退回默认，**不会记住一个点不亮的按钮**。

#### 安卓竖屏：看图还是操作，不用二选一

原先窄屏下整块面板一起滚：主图在上面，下单键在最下面，**必须先滚到最下面**才能在看着图的时候下单 ——
而滚动本身就会把图推走，等于**看图和操作二选一**。现在改成：

- **主图钉在顶部**（`.gg-chart` 36vh），权益曲线也钉在它下面；
- **只有控件区滚动**（`.gg-right` 是唯一滚动容器），账户明细排成两列省高度；
- **做多 / 做空两个大键常驻屏幕最底部**（`.gg-trade > .gg-btns` 用 `position: fixed`）。

于是主图坐标**永远不动**，手指在下单区滑动时图是钉住的。
探针实测（500×848 视口，这是 Windows 上 Chrome 能开的最小宽度）：滚到底时主图坐标不变，
做多键仍落在可视区内，且**没有横向溢出**。

> 一开始用的是 `position: sticky; bottom: 0`，**不行** —— `.gg-btns` 的父级 `.gg-trade`
> 只包"下单区"那一段，滚出父盒之后 sticky 元素会被带着一起滚走（探针实测滚到底时按钮跑到了 y=15）。
> 只能 `fixed`。选择器也必须写 `.gg-trade > .gg-btns`，否则封面卡里那对「开始操盘 / 算了」
> 也会被钉到底部 —— 那个是 `.gg-card .gg-btns`。


#### 两个旋钮，各管一件事

**流速（`SPEEDS`）和重建频率（`TICK_HZ`）是分开的**，这是这套动画的核心设计：

| 旋钮 | 管什么 | 改它会怎样 |
|---|---|---|
| `SPEEDS` | 天气时间走多快（一格 15 分钟花几秒） | 一局变长/变短，**每秒变几次不变** |
| `TICK_HZ` | 一秒重建几次画面 | 画面更细/更顿，**一局时长不变** |

解耦靠的是推进量除以 `TICK_HZ`：

```js
G.acc += (SPEEDS[speedIdx] / barMin()) / TICK_HZ;
//        └─ G.acc × barMin() = SPEEDS 分钟/秒 —— 与 TICK_HZ 无关
```

所以 `u` 的推进速率 = `SPEEDS×60/barMin` 次/秒，**TICK_HZ 只决定"多久采一次样"**。
`TICK_HZ = 4` 表示**无论速度调到哪一档，蜡烛都是 1 秒变 4 次**。

**速度跟 K 线周期也无关**：推进式子里没有 `barMin()`（它只出现在 `G.acc` 的换算里），
所以切换 1 分 / 1 时 / 1 日只是**换一把尺子看同一条时间轴**，时间流速一点不变。
各档一根 K 线的墙钟时长 = `周期分钟数 ÷ 速度`：

| 默认「悠闲」(60 分钟天气/秒) | 1 分 | 5 分 | 15 分 | 30 分 | 1 时 | 4 时 | 1 日 |
|---|---|---|---|---|---|---|---|
| 一根走完 | 1.0 s | 5.0 s | **15 s** | 30 s | 60 s | 4 min | **24 min** |
| 每秒更新 | 4 次 | 4 次 | 4 次 | 4 次 | 4 次 | 4 次 | **4 次** |
| 每次推进 | 0.25 格 | 1.3 格 | 4 格 | 8 格 | 16 格 | 64 格 | **96 格** |

⚠ 表格里"每次推进几格"是指**源样本（15 分钟）**。只有 1 分 / 5 分 / 15 分档每次推进
≤ 1 格；30 分以上一次更新会跨好几格 —— 这是 4 Hz 的必然结果：
**一格里更新几次** × **一根里几格** = **一根几秒 × 4**，三者绑死。

#### 最后那根 K 线是实时在动的

真实行情软件里，**未收盘的那根蜡烛一直在变**：收盘价跟着最新价走、上下影线被不断刷新、
甚至中途由阳翻阴。这一条是后补的 —— 原来的最后那根是**冻住**的：

`tick()` 只在"攒够一整根"时才把现价设成新一根的收盘价，没攒够就直接 `return`（连重绘都不调），
而图上只画到已经走完的那一根。于是**一根越粗，冻得越久**：

| 档位 | 正常速度下多久才推进一根 | 原来的表现 |
| --- | --- | --- |
| 1 分 / 5 分 / 15 分 | 每帧都在动 | 看不出问题 |
| 1 时 | `60/45` ≈ 1.3 秒 | 一顿一顿 |
| 4 时 | `240/45` ≈ 5.3 秒 | 明显是幻灯片 |
| **1 日** | `1440/45` = **32 秒** | **整整 32 秒画面是死的**，然后"啪"地跳一格 |

现在的做法是让光标沿着**真实的 15 分钟源序列**（`G.base`，3552 根）往前走，
最后那一格画成"未收盘"的样子：

```
dpb  = 周期 / 15                        // 一根 K 线 = 几根 15 分钟源
起点 = 上一根的收盘那根源数据             // live bar 的开盘价就是它
终点 = 本根的收盘那根源数据
光标 = 起点 + u × (终点 − 起点)           // u ∈ [0,1] = 这一根的完成度
```

**所以盘中的波动没有一个是编的**，一根 K 线里能穿过多少根真观测完全由周期算出来：

| 档位 | 一根 = 几根 15 分钟真观测 | 探针实测盘中穿过的真采样数 |
| --- | --- | --- |
| 1 分 / 5 分 | 0.07 / 0.33 | 1（在相邻两根源数据之间走） |
| 15 分 | 1 | 2 |
| 30 分 / 1 时 | 2 / 4 | 3 / 5 |
| 4 时 | 16 | 17 |
| **1 日** | **96** | **97** |

1 日档那根蜡烛，一天里会被 **96 个真实的 15 分钟观测**逐格推着走，上下影线取的是
"已经走到的那些真样本的真实极值" —— 不是按比例摊出来的虚构影线。

**收盘瞬间零跳变**是这套算法必须成立的性质：`u` 走到 1 时光标正好落在整数下标上
（`kf = 0`），此时收盘价**精确等于**那根真 K 线的收盘价，高/低也精确等于它。
探针里这条是硬断言：五档 × `u=1` 与 `resample` 出来的真值逐项相等
（误差 < 1e-9，见 `tools/test_live_wick.js`）。

**成交改成按盘中价**（所见即所得）：以前在收盘前下单，成交价是“屏幕上还看不到的
那根的收盘价"；现在按下单那一刻屏幕上那根蜡烛的收盘价成交，挂单和止损止盈同理。
账户权益、浮动盈亏、爆仓距离也跟着逐帧在动，**爆仓因此变成按盘中价触发** ——
更像真实强平，代价是止损被"盘中插针"扫掉的概率变高了。

**性能**：半根那一步不能整个重画（`render()` 会把右栏全部 innerHTML 重建一遍，
1 日档下每秒来 10 次纯属浪费）。所以有一条 `liveTick()` 只做局部重绘。
它的 `setOption` **不能传 `notMerge`** —— 传了就只认那一小份 option，
横轴类别、均线、大盘线、dataZoom 全会被清掉。

> 一个容易踩的坑：ECharts 的 option 合并是
> `!n && i in t || (t[i] = T(e[i]))`，而 `data` 是数组、命中 `Y(o)`（isArray）那条分支
> —— **整个数组被替换，不是逐元素合并**。所以哪怕只改最后一根蜡烛，也必须把
> 可视段整段重传（传一根等于把 90 根蜡烛全删了）。`drawCharts()` 和 `liveTick()`
> 共用同一个 `liveNote()` 来造这些数组，口径就不会漂。

#### 开局先铺 1 周（7 天）历史

这是群里提的：进面板的时候**图表上已经有 1 周连续的 K 线**，实际开始玩是从第 8 天起。

做法是把取到的 3552 根 15 分钟序列切成两段 —— 前 672 根是**预热段**，后 2880 根是**交易段**：

- `resetState()` 把光标停在预热段的最后一根（`G.i = warmBars() - 1`），
  第一根能下单的是 `series[warmBars()]`。
- 顶栏进度按**交易段**算：`已交易 260 / 2880 根`，不是"总共走了 932 根"。
- 图表窗口是 `totalBars()`（7 + 30 天），所以一进来就能看到一段完整的历史走势。
- 改成"一周"之后，`WARM_DAYS` 从 10 缩到 7：预热短了，一进来看到的"来历"更少，
  但交易段（一个月）一根没动 —— 换周期、换城市都不用改别的，全部由 `warmBars()` / `totalBars()` 派生。

> 键盘和按钮在预热段就是好的，`G.i` 一被推到 `warmBars()` 之后才可能成交。

#### 底部副图：成交量 = 天气活跃度

真实行情软件底下都有一排量柱，所以照做了一个。它不是真的成交量（天气没有成交量），
而是**天气活跃度**：

```
活跃度 = 1 + 降水 × 10 + max(0, 阵风 − 6) × 2 + CAPE / 60 + |盘子扰动| × 0.5
```

四个驱动量（降水、阵风、对流能量、盘子扰动）**全是真的**，只有系数是建模的。
量柱按本根涨跌红绿着色，挂在第二个 grid 上，跟主图共用 x 轴、独立 y 轴。
它同时是**插针触发概率**的乘数 —— 活跃度高 = 成交活跃、流动性薄 = 更容易打针。

**本金是真的会改变难度的** —— 这一点上一版写错过，现在靠三样东西成立：

1. **手续费有 ¥5 保底**。名义金额 × 万分之五，不足 5 元按 5 元收（这句是照参考软件抄的）。
   大资金感觉不到，小资金被磨得更狠。
2. **滑点与名义金额成正比**。`滑点(点) = SLIP_K × 名义金额 ÷ 盘子容量`，
   而名义金额 ∝ 本金 —— 所以**滑点占本金的比例随本金线性上升**。
   实测（广州、10 倍、30% 仓）：**30 万本金滑点占本金 0.27%，300 万就是 2.67%**，正好 ×10。
3. **小城市盘子更小**。`盘子容量 = CAP_BASE ÷ dishScale(城市)`，`dishScale` 复用盘子扰动那套
   行政层级分档（县城 2.6、省会 1.0 / 0.7、直辖市 0.53）。同一张单子下到县城，滑点要乘 2.6。

滑点上限（`SLIP_MAX`）定死在 **10 点（指数的 1%）**，这不是美化而是**必需**：名义金额 = 本金 × 仓位% × 杠杆，
滑点于是随杠杆**平方**增长 —— 30 万本金、满仓、100 倍时名义 3 亿，不封顶会算出 300 点滑点，
比 100 倍那条 0.9% 的爆仓线远得多，等于"一开仓必爆"，而且结算卡上会出现
「本金 ¥300,000 · 滑点 ¥896,939」这种荒唐数字（截图真逮到过）。
上限取 **10 点**是折中：300 万 / 30% / 10 倍算出来 9.54 点刚好没被削到，
所以上面那条 ×10 的线性在设计区间内成立；再往上就被封住，
表现为"一开仓就归零"，而不是"欠下比本金还多的滑点"。

当然「30% 仓」那条仍然成立（本金翻 10 倍、手数也翻 10 倍，**仓位盈亏比例**一样），
所以开场卡片的提示把成本直接摆出来，而不是笼统说一句“更难”：
下单卡上那行 **「预估滑点 n.nn 点 · ¥xxx · 本金 x.xx%」** 就是为了让人在按下单键之前先看见代价。

> 顺带把**本机最佳记录从绝对金额改成了收益率**：本金能改之后，「赚了多少万」就没法比大小了
> （本金 1000 万赚 5 万和本金 1 万赚 5 万完全不是一回事）。用新键 `wxgame_bestp` 存收益率、
> `wxgame_bestc` 存当时本金，老的绝对金额记录自然失效，不用做迁移。
>
> 结算卡上还多了一行 **「累计成本：手续费 ¥x · 滑点 ¥y」** —— 打了一局到底被磨掉多少，一目了然。

**爆仓线是这个游戏唯一需要讲明白的数学**：满仓 + N 倍杠杆时，价格反向走 `(1 − 10%) / N` 就被强平 ——
10 倍约 **9%**，20 倍约 **4.5%**，50 倍约 **1.8%**，100 倍只要 **0.9%**。
按指数 1000 点算，100 倍满仓反向动 **9 个点**就没了。所以右侧那 8 行里的
**强平价**和**爆仓距离**是命门，它们一直显示在那儿，价格碰到就结束。

### 挂单与天气日历

这两样是后加的，各自解决一个「光靠手点不够」的问题。

**挂单**。限价单挂在某个价位，价格碰到就按**挂牌价**成交；止损 / 止盈各只能有一张，
触发时全平。几条不那么显然的实现约束（完整版在 [NOTES](docs/NOTES.md)）：

- **挂单要冻结保证金**（`reservedMargin()`）。不冻的话可以靠挂一堆远单把仓位吹到天上 ——
  真券商不是这么干的。冻结之后 `freeEq()` 变成 `权益 − 占用保证金 − 冻结保证金`。
- **成交判定必须带上本根的上下影线**：区间是
  `[min(上一根收, 本根收, 本根低), max(上一根收, 本根收, 本根高)]`，
  只用收盘价的话「插针扫止损」永远模拟不出来。
- **同一根里同时碰到多张单时，按离上一根收盘的距离从近到远依次成交**。
- **`processOrders()` 排在爆仓判定之前**。顺序反了的话，止损单会因为「这一根已经先爆仓了」
  而永远来不及相救 —— 这是写的时候最容易搞反的地方。
- 仓位平掉后，止损 / 止盈自动撤（限价单留着）。
- **滑点只吃市价单**：做多 / 做空 / 一键平仓按不利方向加点成交；**限价单按挂牌价原价成交**
  （“要么按这个价，要么别成交”，代价是可能根本不成交）；**止损止盈照吃**（触发时本质是市价单，
  插针被扫得最惨的正是它们）。没有模拟跳空 —— 真实市场里跳空会按更差的价成交，这里没做。

**天气日历**。它把「未来 24 小时内哪几根 K 线会发生剧烈变化」列出来，
但**只给时间、不给方向** —— 用的是 `|Δseverity|` 的绝对值，方向信息在取绝对值那一步就丢了。
理由和没法做财经日历一样：给了方向就等于剧透这局。界面上那句提示写的是
「就像非农公布前只给 20:30 这个时间」。

强度档不是拍脑袋定的，是照实测分布定的：整局 `|Δseverity|` 的**中位 0.034、p90 0.21、p99 约 2.0、max 约 3.8**，
超过 `JUMP_AT` 的大约只占 **4% 的 K 线**。所以最初定的
「`≥3.4` 剧烈 / `≥1.9` 明显」几乎永远出不来，改成
**`≥2.0` 剧烈 / `≥1.3` 明显 / 其余一般**（分别占 1.0% / 2.4%），条数按 `ceil(d / 0.7)` 最多 4 格。
它和价格里的突发行情用的是同一个 `Δseverity` —— 日历上标出来的每一段，
K 线上**一定**会出现对应的那根长阴 / 长阳，不是两套互不相干的逻辑。

## 数据从哪来

本项目**不生产数据**，只是把公开的官方天气数据画成 K 线。

**一条贯穿全站的原则：以气象局为主，只有气象局缺的那部分才用 Open-Meteo 补齐。**
（2026-10-08 定的，之前不是这样 —— 副图整条线是纯 Open-Meteo，`obList` 还优先吃 Open-Meteo 的日高低温。）

| 数据 | **主供：气象局 / 中国天气网** | 补缺：Open-Meteo |
| --- | --- | --- |
| 实况（气温/体感/风/气压/湿度/降水） | ✅ `Cma.now` | 站点没有实况时 |
| 日高低温 | ✅ 气象局站点预报 → 中国天气网 d1 官方日历 | 官方只给 7 天，第 8 天起 |
| 逐小时 气温/湿度/风速/风向/降水/总云量/低云量/天气码/能见度 | ✅ `Cma.hourly`（3 小时一档，未来 7 天） | 3 小时之间那两小时、第 8 天起、**全部历史 560 天** |
| 紫外线 · 降水概率 · 阵风 · 中/高云 · 露点 | — 气象局这个接口没有 | ✅ |
| 气溶胶 AOD · 空气质量 PM2.5 | — | ✅ |
| 历史逐小时（K 线引擎）· 15 分钟级（游戏） | — 气象局不提供 | ✅ |
| 雷达 / 云图 / 降水预报 / 台风 / 预警 | ✅ | — |
| 地震目录 | ✅ 中国地震台网（CENC，经 Wolfx 转发）+ 美国 USGS 两路合并 | — |

对齐方式是**整点键对齐 + 差值插值**：气象局给的是 3 小时一档，中间那两小时**不是照搬 Open-Meteo**，
而是"以气象局为锚、借 Open-Meteo 的逐时形状" —— 先算出锚点上的差值 `d = 气象局 − Open-Meteo`，
再把它在相邻两锚点之间**线性铺开**加到 Open-Meteo 的逐时值上，锚点本身严格等于气象局的值。

> 为什么必须这么补：两家在同一个整点上**并不一致**（实测 51 个锚点最大差 **5.30℃**、平均 **1.45℃**），
> 照搬式拼接（气象局值 → Open-Meteo 值 → 气象局值）会硬拼出 5℃ 的尖角，
> 7 日分时看上去全是锯齿。实测扎手程度（平均 |二阶差分|）从 **1.9387 → 0.4038**，降到 1/4.8。
> 两个字段**不插值**：**降水**和**天气码**（分类码 / 多为 0，插出来是假的），只在锚点上覆盖。
> 实现是 `API.overlayCma()`，主表与副图共用同一条规则。另外分时折线开了 `smooth: 0.25`
> （不是 `true`，那会过冲），折角不再那么硬。

> **逐条端点、参数、粒度、代理路由、踩过的坑 → [docs/APIS.md](docs/APIS.md)**（含"试过但没用上的"那一节）。

### 口径与取舍（写在界面上嫌啰嗦，但得有个地方记着）

**界面上只留三类注脚**：① 精度（能不能拿它对表）② 名词定义 ③ 会让人误解的地方。
其余一律写在这里或 `docs/NOTES.md` —— 界面是给看天气的人用的，不是开发日志。

#### 天文

* **日出日落精度**：拿 `sunrise-sunset.org`（NOAA 那套，另一份代码）对了 **30 组**
  （北京 / 广州 / 拉萨 / 漠河 / 三亚 / 曾母暗沙 × 2026 春分 / 夏至 / 秋分 / 冬至 / 10-08）：
  **日落差 1.07～2.35 分钟**（漠河最大），**日出 0.2～3.1 分钟**。
  界面统一写「0.2～2.4 分钟」。差异来自 `sunEvents` 的 **2 分钟粗扫步长**与两套近似式的取法不同。
  ⚠ 对照时注意**日期口径**：`sunEvents` 的窗口是 **UTC 整日**，东八区窗口里装的那次日升
  其实是**次日清晨**的（03-20 的窗口里是本地 03-21 06:16 = 03-20 22:16Z），
  所以比日出要允许前后挪一天 —— 否则会看到一个漂亮但毫无意义的「+1440 分钟」。
* **观星评分为什么这么配分**：低云 40 · 中高云 25 · 降水 12 · 湿度 6 · 风 6 · 月光 6 · 通透度 5
  （AOD 与能见度取更差的一个）；低云 ≥70% 直接封顶 45 分、≥90% 封 20 分 ——
  云是观星唯一的天敌，别的项再好也救不回来。
* **「全年气候」怎么算的**：取近 10 个完整年的逐日**全天平均**云量（一次约 59 KB，缓存 30 天），
  把「全天平均 < 30%」记作一个少云夜。它**看不见夜里那一段**，所以会**低估**晴夜数
  （白天云多、夜里放晴的日子被算掉了）。拿来比"哪个月更值得来"够用。
* **视直径为什么只给一个数**：近地点约 0.56°、远地点约 0.49°、满月平均 0.518°，
  差值肉眼分不出来（只有拍照党在意）。「偏近 / 偏远」写在**距离**那一行 ——
  视直径的变化本来就是距离造成的，两行都说一遍是重复。
* **「已落下」的口径**：按**天体中心**算。月面视直径有半个度，满月刚落下的那几分钟，
  上半边其实还露在地平线上。
* **日月食为什么没做**：找过 NASA/USNO 那几个免费源，本机要么域名解析不了、
  要么没有可直连的接口；硬编码一张表又没法当场核验 —— 宁可先不写（宁可没有，也不要写错的日子）。
* **极光页与日月页的分工**：按**因果链**划。耀斑 → 太阳风 → Bz → Kp → 极光，四段都在极光页
  （拆开就断了因果）；太阳**自身**的方位、高度、日地距离、正午高度角归日月页；
  太阳黑子数留在极光页，因为它是这条链的**背景强度**（一整个月的活动水平）。
* **日月页一个网络请求都不发**：所以太阳黑子数与耀斑等级**故意不放这一页** ——
  那两个要打 NOAA，会把"本页不联网"这条破掉。想往这一页加东西之前先问：它能不能本地算？
* **霞**：没有免费的霞预报接口，所以那一页是自拟启发式，只看中高云够不够当画布、
  低云会不会挡死地平线、气溶胶够不够浓（AOD 0.1~0.4 最出红，>0.7 反而发浑）。
* **此刻页也不联网**：亮星用耶鲁亮星表的 J2000 坐标、行星用 JPL 的简化开普勒根数、
  月亮距离用 Meeus 的简化级数。用途是"抬头往哪看"，不是精密天体测量。
* **流星雨表是离线的**：只有「活动期 / 辐射点 / 母体」常年不变；年份是**运行时现推**的，
  所以不存在"过完今年就失效"（12/31 打开会直接给出明年 1 月 3 日的象限仪座）。
  「ZHR」是常年参考值而不是今年的预测 —— 象限仪座在 60～200 之间年际起伏，天龙座 2011 年爆到 600+。

* **潮汐给的是「天文潮」，不是「预报水位」**：按 50 个分潮的调和常数求和算出来，
  不含台风风暴增水与气压效应 —— 天文大潮叠上台风时，实际水位会比它高一两米。
  水位相对**平均海平面**，所以低潮时是负数。**精度**：拿香港天文台的官方逐时预报对了
  744 个整点，去掉两套基准面之间的常数差之后**平均绝对差 0.036 米**（p90 0.069、最大 0.158），
  整月潮差两边都是 **2.13 米**。
* **潮汐是"借站"**：调和常数是**按站**给的（16 个站），所以每座城市都用**离它最近的那个站**，
  界面上写明站名与距离；超过 150 公里就不借了，直接说这附近没有可用的潮汐站。
  352 个城市里只有 44 座能落到站上。
* **光污染是 1~9 级，不是波特尔（Bortle）**：取 David Lorenz 地图集每座城市 5×5 像素
  （约 4.6 公里）的**中位值**，给的是**天顶人工亮度**的模拟值；作者明确要求两者别混为一谈，
  所以界面上一个"波特尔"字都没有。定位（没有城市条目）时按经纬度直接查网格
  （0.025°，约 2.8 公里），取 9 像素的**多数**。
* **行内对齐的唯一基准是"不变的那一侧"**：数值列贴着不变的那端对齐（`82 米`、`68 分`），
  而 `→`、`～`、`/` 连接的两个值时，**以连接符为基准** —— 三格定宽，连接符落在同一条竖线上。
  这条规矩在全站五处落地（日月的时间段、此刻星空的今夜时段、观星页的云列、潮汐两张表的日期、
  流星雨的活动期）。

#### 收藏城市为什么要预热

切换收藏城市时要等一次取数，所以会稍微卡一下；而收藏这座城市本身说明它的查看频率更高，
没收藏的城市更加频繁。」两个原因叠在一起：

1. `API.Store.loadCity()` 只在「打开页面 / 切城市 / 30 分钟全量重载」时被调用，
   所以**除当前这一座以外，其它收藏城市永远没有快照**；
2. 城市快照原来只留**最近 2 座**（`CX_KEEP = 2`），连"上次看过的那座"都很快被挤掉。

现在 `web/js/app.js` 里的 `warmCities()` 会在当前城市画完之后，趁空闲**串行**把其余收藏城市
一座一座补进缓存（只喂缓存，不碰 DOM）。三条约束：**串行且每次都让开前台**
（`S.loading` 为真就等，绝不跟切城市抢带宽）、**只在快照真的过期时才跑**（20 分钟内不动）、
**省流模式与 2G 不跑**（`navigator.connection`）。

**能留几座是量出来的，不是定的**（`tmp/cap.js` / `tmp/cap2.js`，桌面 Chrome）：

| 量的是什么 | 结果 |
| --- | --- |
| 一份快照多大 | **339～359 KB**（隔省抽 12 座）；把 `daily[].hours` 这个没人读的中间产物扔掉后 **273～294 KB** |
| localStorage 真实配额 | **5086 KB** —— 往死里塞到 `QuotaExceededError` 量出来的（5 MB 按 UTF-16 码元算），不是猜的 |
| 硬上限 | 5086 / 289 ≈ **17 座** |

所以现在 `CX_KEEP = 12` + **`CX_BUDGET = 3600 KB`** 双闸门（座数到顶、或预算不够，从最旧的
那头淘汰）。`web/js/app.js` 的 `WARM_MAX` 直接读 `API.Store.snapshotKeep` **跟它对齐** ——
预热得比缓存多，多出来的那座下一轮必定已被挤掉，于是每轮都在重拉同一批，白烧 Open-Meteo
额度而且用户完全感觉不到。`WARM_GAP = 1200 ms`（12 座 × 6 请求 / 1.2 s ≈ 300 次/分钟，
Open-Meteo 上限是 600 次/分钟，还得跟行情轮询分）。

⚠ **别再写 `storeSet(k, null)` 当删除用** —— 它 `JSON.stringify(null)` 之后存进去的是
4 个字符的字符串 `"null"`，键还在、占地方、遍历时还会被当成一份有效数据。要删用 `U.storeDel(k)`。

#### 免责声明里被搬走的那些话

2026-10-08 定下的两条口径（其实是同一条）：
① 天文模块抽屉下方的注脚太多，要区分「写给开发者看的」与「写给用户看的」，
前者写进本文档、不要留在界面上；
② 功能免责声明要补全，语气面向用户（可以可爱、可以用颜文字），
对象是用户而不是开发者。

所以界面上那张 `#welcome` 免责声明现在**只讲用户需要知道的**（数据来源署名、哪些是本站自己
算的、几件容易误会的事、隐私），而下面这几段"为什么是这样"的说明从界面上搬到了这里：

* **地震那两路为什么经 Wolfx 转发**：中国地震台网与日本气象厅自己的站点**响应 200 却不给跨域头**，
  浏览器直连读不到；Wolfx（`bs.wolfx.jp`）那份公开接口带 `Access-Control-Allow-Origin: *`，
  所以借它转发。USGS 那一路是直连的，用来补 130 天窗口与全球覆盖。
* **观星页「全年气候」的实现**：取 Open-Meteo 归档接口近 10 个完整年的逐日**全天平均云量**
  （一次约 59 KB，本地缓存 30 天），把"全天平均 < 30%"记作一个少云夜。它看不见夜里那一段，
  因此会低估晴夜数。
* **光污染的取法**：David Lorenz 的 Light Pollution Atlas（`djlorenz.github.io/astronomy/lp/`，
  2025 版，由 VIIRS 夜间灯光经大气传输模型推算）。本站**离线取好**，每座城市按 5×5 像素
  （约 4.6 公里）窗口中位取一个值，运行时只查表。它给的是**天顶人工亮度**的模拟值，
  **不是波特尔（Bortle）等级** —— 后者是肉眼主观评级、看的是整片天，作者明确要求两者别混为一谈。
* **海表温度（NASA GIBS）是卫星融合产品，有几天延迟**；「🌡 海陆温」里陆地那一档仍是中央气象台
  的全国气温实况图。数据挂错来源跟"自行更改预报内容"是同一类问题，所以界面上把两者分开写。
* **地震预警（EEW / 紧急地震速报）**：来自日本气象厅、中国地震台网、四川省地震局、福建省地震局、
  重庆市地震局、台湾气象署，同样经 Wolfx 转发。这几条是各机构的**最新一次发布**、
  不代表此刻正在发生 —— 界面上写明"多久之前"，只有 30 分钟以内的才按告警显示。
* **台风那条线的两段**：实线是已经走过的定位，虚线是中央气象台的官方预报；强度可能比实际慢半拍。
* **预警信号的排序是本站排的**（红→橙→黄→蓝），原文照搬、是否生效以官方为准。
* **APK 是本机自己签名的**（`android/debug.keystore`，不是应用商店渠道），
  安装时系统会提示"来源不明"；它也**不会自动更新**，升级要回来重新下载。

## 城市范围

当前收录 **352 个城市**（全国地级市，`web/data/cities.json`，50 KB）：

- 每个城市带中国天气网 city id、经纬度、拼音、省份
- 其中 **310 个**有中国气象局官方站号，剩下 42 个（佛山、惠州、江门、肇庆、香港……）
  没有站号，走 Open-Meteo 实况，界面上会标「无官方站号」

**搜索框搜得到全部 352 个**，不是只有预置的那几个。

在此之上还有一份 **省 / 地级市 / 区县三级地名目录 `web/data/places.json`**（3237 条，
222 KB，来自阿里 DataV 的行政区划边界数据，每条带中心点经纬度）：**义乌、昆山、敦煌、
察隅、漠河、浦东新区**这类县级市 / 区在这里才搜得到，`cities.json` 只有地级市所以没有它们。

- 搜到的区县没有气象局站号，但**带经纬度**，直接按坐标走 Open-Meteo 取天气 —— 与
  「当前所在地」是同一条通路，蜡烛图、副图、叠加线、雷达（挑最近的有站城市）都正常
- 下拉里区县会标出上级：`义乌市 | 浙江省 · 金华市 | 区县`
- `tools/build_places.py` 会逐级爬 DataV（1 + 34 + 475 次请求）重新生成它；
  地级市里已经有站号的会被去重，避免同一城市出现两条

> ⚠️ 这里踩过一个坑：早先为了控制仓库体积，用 `tools/scope_cities.py` 把目录裁到了 45 个城市，
> 结果**顺手把搜索能力也砍掉了** —— 目录就是搜索的唯一数据源。现在目录保持全量
> （352 地级市 + 2903 区县），体积改由「预抓范围」单独控制：`cities.json` 里的 `prefetch`
> 字段列出 45 个重点城市（`tools/prefetch_official.py` 默认只抓这些），想全抓加 `--all`。

> 浏览器自带的定位、以及第三方地理编码接口都试过，**对中国区县都不可靠**：
> Open-Meteo 的 geocoding 对「昆山」返回的是福建三明的一个同名村，「敦煌」「察隅」干脆 0 命中。
> 所以最终没有用联网地理编码，而是把 DataV 的行政区划目录**离线打包进来**，搜索走本地索引。

### 当前所在地

左栏最上面一栏是 **当前所在地**，用浏览器 / 系统的定位权限取坐标，**再把坐标换算成具体区县**：

1. BigDataCloud 反查地名（`localityLanguage=zh-Hans`）
2. 同时算出最近的城市和距离，显示成 `广州市 · 广东省 · 近 佛山 18 km`

天气是**直接按经纬度取的**（Open-Meteo 逐小时 + 历史），不是拿最近城市的天气替代 ——
所以报价头会标「无官方站号」。反查失败也不影响出天气，名字退化成「近 <最近城市>」。

- **点那一行才要权限**：加载时不会静默调 `getCurrentPosition`，只有浏览器已经授权过才静默刷新
- 首次访问才会自动切到当前位置；用 `?city=` 或上次打开的城市明确指定过就不劫持
- 位置记在 `localStorage`，30 分钟内不重复定位
- 拒绝授权、定位超时都各有文案提示，不会静默失败

> ⚠️ **权限提示一辈子只弹一次。** 早先的实现在页面加载时就调 `getCurrentPosition`，
> 用户在没预期的情况下把提示点掉（或拉黑），权限就永久变成 `denied` ——
> **再点也弹不出来了**，表现为"点了没反应"。现在改成：
> `navigator.permissions.query({name:'geolocation'})` 先看状态，
> `prompt` 状态下一个字都不问（等用户点），`denied` 时文案改成
> "已被浏览器禁止 · 点地址栏 🔒 把「位置」改成「允许」后点这里"，
> 因为 Chrome 确实不会再弹了，只能引导用户自己去改站点权限。

> **坐标换算全在本机做**，只有反查地名那一步会把坐标发给 BigDataCloud；
> 天气数据本身是按坐标查 Open-Meteo 的，不经过任何中间服务器。

### 指数条

顶栏那一排（`北京 14.8 -0.90 -5.73% ︿`）就是左栏 **「当前位置 + 自选城市」的镜像**，
顺序和左栏一致，**点一下就能切城市**，当前城市高亮。

> 它以前是写死的沪/深/京/穗/湘五个城市，外加一个 computed 的「自选均温」（自选城市的平均气温）。

## 发布到自己的仓库

这台机器上通常没有装 `git`，而 GitHub 从 2021-08-13 起就不再接受账号密码做 API 调用，
所以推送走 **GitHub REST API（Git Data API）**，只需要一个 Personal Access Token：

1. <https://github.com/settings/tokens/new>
2. 勾 **`repo`**（必需）+ **`workflow`**（必需，否则 `.github/workflows/` 下的文件会被拒收）
3. 生成后：

```powershell
$env:GH_TOKEN = "ghp_xxxxxxxx"          # 也可以直接 --token 传

```

推送完 Pages 会自动开始构建（`.github/workflows/deploy.yml` 首次由 `push` 事件触发）。
大约 1~2 分钟后站点在 `https://<用户名>.github.io/weather-fighter/`。

> **仓库必须是 public**：免费账号的 Pages 不支持私有仓库（私有仓库开 Pages 需要 GitHub Pro）。

## 数据自动更新

`.github/workflows/deploy.yml` 每 30 分钟跑一次：

1. `tools/prefetch_official.py` 带着正确的 `Referer` / `UA` 抓中国天气网与气象局的数据，写进 `web/data/official/`
2. 有变化就 `git commit && git push`
3. 把 `web/` 整个发布到 GitHub Pages

> 抓数据和部署**必须写在同一个 workflow 里** —— 用 `GITHUB_TOKEN` 推送产生的 commit
> 不会触发其它 workflow，拆成两个文件的话 Pages 永远不会更新。
